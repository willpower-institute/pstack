# ADR-0001: สาขาทำ frontend ได้เอง · ส่วนกลางเป็น backend of record · เชื่อมผ่าน contract เดียวต่อโดเมน

- สถานะ: **proposed** — รออนุมัติจากเจ้าของงาน (decision `dec-fc13090f` บนโต๊ะกลาง ws-001)
- วันที่: 2026-10-21
- ที่มา: คำยืนยันของเจ้าของงาน (monthop-gmail) ในกระทู้ `dis-65134078` seq 69–70
- ขอบเขต: ทุก repo ใน `willpower-institute/*` และ `pstack-*` ของ monthop-gmail

## บริบท

- ส่วนกลางของสถาบันพลังจิตตานุภาพ **ไม่มีระบบกลาง** สำหรับผลการเรียน/ผลสอบ/ยอดกิจกรรม
  ณ วันนี้ record ทางการคือไฟล์ Excel/PDF ต่อรุ่นที่สาขาส่งมูลนิธิผ่านไดรฟ์
- ส่วนกลางอนุญาตให้ **แต่ละสาขาทำ frontend ของตัวเอง** แล้วมาเชื่อมกับระบบกลาง
  และจะปรับ **ทุกหลักสูตรและทุกกิจกรรม** เป็นรูปแบบนี้ทั้งหมด
- มี frontend ที่สาขา/ทีมทำไว้แล้ว เช่น `vitunclass5` (วิทันตสาออนไลน์ Next.js)
  และ `vitisa76m` (แคมเปญ 76 ล้านนาที static 3 หน้า) — ทั้งคู่ยังเก็บข้อมูลเอง ไม่มี backend กลาง
- กฎของแต่ละหลักสูตรเปลี่ยนตามเวลา (วิทันตสาออนไลน์เปลี่ยนอย่างน้อย 4 ฉบับระหว่าง
  พ.ค. 2564 – เม.ย. 2565; ห้องเรียนเปลี่ยนจากฉบับ 2556 → 2564) และต่างกันระหว่าง
  ระบบห้องเรียน/ออนไลน์ — ถ้า frontend แต่ละตัวคิดคะแนนเอง ยอดจะไม่ตรงกันและตรวจย้อนไม่ได้
  (บทเรียน `LEGACY_RULES.md` ของ pstack-vidhisa)

## การตัดสินใจ

### 1. บทบาท

| ส่วน | หน้าที่ | ห้าม |
|---|---|---|
| **frontend ของสาขา** (เว็บ, LINE, Google Form, แอปที่สาขาทำเอง) | รับ evidence จากผู้เรียน/ผู้ปฏิบัติ · แสดงผลที่ส่วนกลางคำนวณแล้ว | คิดคะแนน/ยอดเอง · เข้า DB กลางตรง |
| **reference frontend กลาง** (1 ตัวต่อโดเมน, ส่วนกลางส่งให้) | ใช้งานพื้นฐานได้ทันที · เป็นฐานให้สาขา fork/ต่อยอด | ใช้สิทธิ์หรือ API ที่ frontend สาขาไม่มี |
| **backend of record** (pstack + addon ต่อโดเมน) | system of record · ถือ rule set · คำนวณคะแนน/สิทธิ์/ยอด · ออก completion/ผลทางการ | รับคะแนนที่คิดแล้วจาก client |

reference frontend กลางต้องใช้ **contract เดียวกับสาขา** (dogfooding): ถ้าตัวกลางต้องการสิ่งที่
contract ไม่มี แปลว่า contract ยังไม่พอ ไม่ใช่เพิ่มทางลัดให้ตัวกลาง

### 2. ทิศข้อมูล

สาขาส่ง **evidence ดิบ** ต่อคน ต่อเหตุการณ์ (เข้าเรียนหัวข้อ X วันที่ Y · การบ้านครั้งที่ n ·
นั่งสมาธิ 5 นาที ช่วงเช้า) พร้อม source reference ของสาขา · ส่วนกลางเป็นผู้ตีความตาม
กฎที่มีผล **ณ วันที่เกิดเหตุการณ์** · การบันทึกต้อง idempotent (ส่งซ้ำไม่นับซ้ำ)
และการแก้ไขเป็น supersession ที่มีประวัติ ไม่ใช่เขียนทับ

### 3. Deliverable ต่อโดเมน — 3 ชิ้นเสมอ

1. **backend addon** บน pstack: rule set + evidence ingestion + ผล
2. **integration contract**: auth แบบ per-branch, endpoint บันทึก evidence, endpoint อ่านสรุป/สิทธิ์/อันดับ,
   fixture ทดสอบ, คู่มือเชื่อม
3. **reference frontend กลาง**: ใช้ contract ข้อ 2 เท่านั้น

โดเมนแรก: **campaign** (วิทิสา 49M/76M) เพราะ engine ของ pstack-vidhisa ผ่าน parity 9 ชั้นแล้ว
และต้นแบบ 76M เป็น UX reference พร้อม · โดเมนถัดไป: LMS (ครูสมาธิ/วิทันตสา) · thudong

### 4. Identity กลาง (ค่าตั้งต้น ปลดล็อก B001/B002)

- **PersonRef** = รหัสนักศึกษา 10 หลักตามคู่มือ (3 หลักท้าย พ.ศ. + ลำดับ 7 หลัก)
  สำหรับหลักสูตร · ผู้ร่วมกิจกรรมที่ไม่ใช่นักศึกษาใช้รหัสผู้ร่วมกิจกรรมที่ส่วนกลางออก
- **BranchRef** = รหัสสาขาตามทะเบียนสาขาของมูลนิธิ
- frontend ทุกตัวต้องอ้าง ref เหล่านี้ · ห้าม match ด้วยชื่อ (บทเรียน name-based cap ของ 49M)

### 5. กฎ version ตามเวลา

ทุกโดเมนเก็บ rule set ที่ key ด้วย `(หลักสูตร/กิจกรรม × ระบบ × effective_date)` และ
ประวัติกฎเก่าต้องยังรันได้เพื่อ replay รุ่นเก่า · ตัวอย่างชุดเริ่มต้นของ LMS:
ห้องเรียน-2556, ห้องเรียน-2564, ออนไลน์-2564-12, ออนไลน์-2565

### 6. สิ่งที่ตั้งใจไม่ทำ

- **ไม่บังคับ migrate** frontend ที่สาขามีอยู่เข้า pstack — บังคับแค่ "ต่อผ่าน contract"
- **ไม่ใช่ multi-tenant**: สาขาคือ orgunit ภายใต้สถาบันเดียว ใช้ orgunit hierarchy + RBAC scope
  (ตามที่ตัดสินใน pstack-vidhisa spec §7)

## ทางเลือกที่ไม่เลือก

- **ส่วนกลางทำ frontend เดียวบังคับทุกสาขา** — ช้า และขัดกับนโยบายที่สาขาเริ่มทำเองแล้ว
- **สาขาทำเองหมด ไม่มีตัวกลาง** — สาขาเล็กไม่มีกำลัง; ตัวกลางพื้นฐานทำให้เริ่มได้เร็วกว่า
- **frontend คิดคะแนนแล้วส่งยอด** — ยอดไม่ตรงกันข้ามสาขา ตรวจย้อนไม่ได้ (เกิดแล้วกับ 49M)
